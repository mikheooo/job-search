# GIG-SEARCH P5 — адресный поиск и очередь «куда подаваться сейчас»

Цель P5 — не улучшать систему ради улучшения, а **быстрее находить заказы, на которые можно податься сейчас**. Система перестала ранжировать случайную общую выдачу: она ищет целенаправленно и отвечает на вопрос «на что подаваться сегодня».

Главный результат — файл `docs/gig_search_p5_queue.md`: **15 заказов в APPLY_NOW** с блоками WHY / RISKS / WORK / MONEY по каждому.

---

## 1. Адресный поиск (§1)

Разведка подтвердила, что это возможно без обхода ограничений:

| Проверка | Результат |
| :--- | :--- |
| `/jobs/<skill>/` | работает, 10 из 10 направлений дают проекты |
| robots.txt | запрещает только query-форму `/jobs/?*`; путевая форма разрешена |
| Разметка | та же, что у общей ленты (`JobSearchCard-iteminner`, 50 карточек) |
| Пагинация | `/jobs/<skill>/<N>` работает, **0 пересечений** между страницами |

Добавлены **20 целевых направлений**: python, api, automation, rest-api, web-scraping, data-processing, excel, data-entry, django, flask, fastapi, postgresql, sql, telegram, chatgpt, openai, llm, artificial-intelligence, n8n, zapier.

Сбор стал **двухфазным**, и это не оптимизация, а исправление логики. В первой версии проект отдавался при первой встрече, поэтому `found_via` никогда не набирал второе направление — поле оставалось с одним значением. Теперь сначала строится карта направлений, потом читаются детали:

```
ФАЗА 1: обойти все страницы выдачи → карта «проект → направления»
ФАЗА 2: читать детали один раз на уникальный проект
```

Побочный эффект: один проект = один запрос деталей, даже если найден пятью направлениями.

## 2. Дедупликация и `found_via` (§2)

Дедуп теперь по **двум ключам**:

* по URL выдачи — чтобы проект из нескольких направлений читался один раз;
* по **`source_id`** — потому что источник может отдать два разных URL на один проект.

Второй ключ появился после измерения: при одинаковом ответе на разные URL получалось **5 записей с одним `fl_40741883`** вместо одной. Дедуп по URL этого не ловил.

`found_via` хранится в `source_facts`:

```json
"found_via": ["api", "automation", "python"]
```

**`found_via` не влияет на score.** Это прямо требуется в §2, и это проверено тестом: заказ, найденный через одно направление, и тот же заказ через четыре получают одинаковый `action_score`. Иначе проект дорожал бы от числа поисковых запросов, а не от своей сути.

Покрытие на итоговом корпусе:

| Метрика | Значение |
| :--- | ---: |
| Записей Freelancer | 430 |
| С `found_via` (собраны адресно в P5) | 148 |
| Найдены через 2+ направления | **64** |

282 записи без `found_via` собраны до P5 через общую ленту — это честно отражено, а не додумано задним числом.

## 3. Money-First признаки (§3)

### competition — пороги выбраны по данным

Распределение ставок на первых 296 записях дало перцентили: p50=10, p75=29, p90=63, p95=106. Границы 10/25/50/100 из ТЗ **совпали с фактическим распределением**, поэтому приняты:

| Полоса | Ставок | Оценка |
| :--- | :--- | ---: |
| excellent | 0–10 | 100 |
| good | 11–25 | 78 |
| medium | 26–50 | 52 |
| hard | 51–100 | 26 |
| very_hard | 100+ | 8 |
| unknown | нет данных | 45 |

`unknown` намеренно **не** равен `excellent`: неизвестная конкуренция не должна выглядеть выгоднее известной низкой.

### freshness

`under_1h` / `under_6h` / `under_24h` / `1_3_days` / `over_3_days`. Если времени нет — `unknown`, и оно **не** считается свежим. Отрицательный возраст (часы разошлись) приводится к нулю, а не показывается как есть.

### estimated_effort_hours и ставка

Трудоёмкость выведена в результат: она напрямую влияет на прибыльность fixed-price заказа. Эффективная ставка использует готовую P4-конверсию:

| Случай | Значение |
| :--- | :--- |
| hourly | нормализованная ставка в USD |
| fixed | бюджет ÷ трудоёмкость, в USD |
| нет курса или трудоёмкости | `None`, не подставленное число |

Неизвестная ставка не удаляет заказ, но снижает уверенность: балл ограничивается 60, и в `notes` появляется `rate_uncertainty`.

## 4. Action Score (§4)

Старый `score` **не удалён** и не переписан. Добавлен отдельный показатель, отвечающий на другой вопрос:

| | Вопрос |
| :--- | :--- |
| `opportunity_score` | насколько проект хорош вообще |
| `action_score` | разумно ли податься на него **сейчас** |

Формула прозрачная, не ML:

| Компонент | Вес | Что учитывает |
| :--- | ---: | :--- |
| `base_score` | 30 | существующий opportunity_score |
| `competition` | 20 | число ставок |
| `rate` | 18 | эффективная ставка USD |
| `freshness` | 16 | возраст объявления |
| `skill_fit` | 10 | совпадение навыков |
| `deliverability` | 6 | can_deliver |

Каждый вклад виден в breakdown с пояснением. Пример (заказ №1 из APPLY_NOW):

```
action_score: 73.8
components: base_score=70.0 competition=78.0 freshness=72.0
            rate=92.9 skill_fit=30.0 deliverability=100.0
notes:
  base_score:    opportunity_score=70.0
  competition:   good (15 ставок)
  freshness:     under_24h (14.4 ч)
  rate:          $37.5/ч при оценке 34.4 ч
  skill_fit:     match=30
  deliverability: can_deliver=high
```

Два жёстких правила (§5) отражены в `notes`, а не спрятаны:

* `can_deliver=low` → потолок 44 (`deliverability_cap`);
* ставка не подтверждена → потолок 60 (`rate_uncertainty`).

## 6. Три дефекта, найденные по ходу

### Дефект 1: навык `make` считался совпадением с английским глаголом

В профиле есть `make` (Make.com). Слово-границы матчили обычное «make» в тексте, поэтому **29 заказов** получали совпадение навыка и поднимались до `can_deliver=high`:

```
Whole House Interior Design          matched=['make']
Armenian Spiritual Book Proofreading matched=['make']
Photo Board to Wall Art              matched=['make']
```

Исправлено: неоднозначные короткие слова (`make`, `llm`, `git`, `bash`) требуют подтверждающего контекста. «Make.com scenario» — совпадение; «make a logo» — нет. После правки: **29 → 0**.

### Дефект 2: не-IT домены проходили как выполнимые

Из-за дефекта 1 видео- и контент-работы попадали в топ. Добавлен признак `non-IT domain` (видео, звук, графика, копирайтинг, перевод) с важной оговоркой: он срабатывает **только без явного IT-признака**. Заказ «Video platform API integration» — это интеграция, и он не отбрасывается.

### Дефект 3: решение без причины

Одна запись уходила в MAYBE без объяснения: балл ниже порога, но недостатков не было. Добавлена причина `below the apply-now threshold`. Также переименована вводящая в заблуждение подпись: `posting too old` → `posting not fresh (over 24h)`, потому что это **не** SKIP-порог 72 ч, а критерий «уже не первой свежести».

## 7. Данные реального сбора (§9)

Корпус: **430 записей Freelancer** (было 296), 425 оценено.

| Метрика | Значение |
| :--- | ---: |
| Уникальных проектов собрано адресно | 130 за 150 запросов, 0 ошибок |
| Дублей убрано | **128 из 130** (почти всё уже было в базе) |
| `found_via` размечено | 148 |
| Найдено через 2+ направления | 64 |

**Что показал этот результат честно:** целевой сбор нашёл почти то же, что уже лежало в базе. Причина не в поломке дедупа (он сработал), а в том, что корпус наполнялся теми же публичными страницами. Прирост дал 2 новых проекта. Чтобы адресный поиск давал больше, нужно либо больше страниц внутри направления, либо более узкие направления.

### Распределения

| По выполнимости | | По ставке USD | | По возрасту | | По ставкам | |
| :--- | ---: | :--- | ---: | :--- | ---: | :--- | ---: |
| low | 251 | < $2/ч | 154 | under_6h | 12 | excellent (0–10) | 168 |
| high | 118 | $2–5/ч | 56 | under_24h | 205 | good (11–25) | 79 |
| medium | 54 | $5–15/ч | 148 | 1_3_days | 168 | medium (26–50) | 62 |
| | | $15–40/ч | 37 | over_3_days | 38 | hard (51–100) | 51 |
| | | $40+/ч | 10 | | | very_hard (100+) | 63 |
| | | неизвестна | 18 | | | | |

**Важный факт о рынке:** 154 из 425 (36%) имеют ставку **ниже $2/ч** после конверсии. Это не дефект расчёта, а реальность Freelancer: там много заказов из регионов с низкими ставками. Именно поэтому APPLY_NOW оказался таким узким.

### Старый score против action_score

Пересечение топ-15 по двум метрикам: **9 из 15**. То есть `action_score` **не** повторяет старый ranking — меняется 6 позиций из 15.

Ключевое отличие видно на примере: заказ «Django Backend Development with PostgreSQL» имеет высокий старый score, но **89 ставок**, поэтому по action он падает. А «E-commerce Text and Image Scraper» со **ставкой $20/ч, 29 ставками и возрастом 0.6 ч** поднимается.

## 9. QA (§11)

```
pytest tests/gig -q
→ 434 passed

pytest tests -q
→ 2 failed, 3448 passed in 504.23s
```

Оба падения существовали **до P5** — это те же два, что и в P4 (там было «2 failed, 3376 passed»).
Ни одного нового отказа.

| Отказ | Класс | Доказательство (измерение, а не заявление) |
| :--- | :--- | :--- |
| `test_report_line_refs.py::test_the_report_has_no_new_symbol_mismatches` | `UNRELATED` | Прогнал чекер с моей правкой `cli.py` и с байтово-откаченной: **75 и 75** — идентично. Правка P5 ограничена ровно 506 байтами в блоке gig fetch, далеко ниже цитируемых строк (диапазон ссылок 448–7011, вставка — у парсера `gig fetch`). |
| `test_candidate_master_resume.py::test_a_project_sync_does_not_touch_resume_or_interview_claims` | `UNRELATED` | Файл застейджен чужим `git add` (статус `A` в индексе), mtime 24.09. Правки P5 его не касались. |

**Про `cli.py` отдельно.** Первые две правки P3 меняли его байтово, и там же лежит bare-CR
разметка, на которую ссылается triage-отчёт. Поэтому каждая правка в этом файле проверяется
обратной подстановкой: если она не даёт исходный sha256, правка не ограничена — и это повод
не считать её безопасной. В P5 обратная подстановка сняла ровно 506 байт и вернула файл в
исходное состояние.

**Как классифицировались падения:** сначала измеряется, зависит ли результат от моей
правки; только после этого ставится `UNRELATED`. Чужое падение не объявлено чужим без
измерения.

## 10. Ограничения

| Ограничение | Факт |
| :--- | :--- |
| **Адресный сбор дал мало нового** | 128 из 130 — уже известные проекты. Причина: те же публичные страницы. Больше прироста даст углубление (`--skill-pages`) или более узкие направления |
| **36% заказов ниже $2/ч** | Реальность рынка Freelancer, не дефект расчёта. Это и объясняет узость APPLY_NOW |
| **Трудоёмкость — эвристика** | Влияет на fixed-ставку и на action_score. Модель прежняя, я её не менял |
| **Рейтинга и истории клиента нет** | Источник не публикует — поэтому RISKS честно говорит «данных о клиенте нет» |
| **`non-IT domain` требует IT-признака** | Заказ с API-интеграцией и словом «video» не отбрасывается, но заказ про монтаж с упоминанием «сметы в Excel» может пройти. Порог настраиваемый |
| **`found_via` только у 148 из 430** | Остальные собраны до P5 через общую ленту |
| **Курсовая история не ведётся** | Используется курс на момент сбора (сознательно исключено §8) |
