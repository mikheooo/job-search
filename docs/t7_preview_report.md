## 1. Часть 1 — дефект и минимальная правка

### 1.1 Что было не так

`load_vacancy_facts` в `ai_assistant/candidate/job_brief.py` вытаскивал технологии требования через
словарь KB (`_kb_vocabulary`, 57 записей, 41 каноническая форма). Словарь строится только из
claim'ов видов `skill`, `project_stack`, `role_title` — то есть из того, что кандидат уже умеет.
Название, которого в словаре нет, в требование не попадало вообще.

Отсюда два следствия, и оба — в опасную сторону:

- требование выглядело короче, чем оно есть (`Docker; … (GitLab CI, GitHub Actions, Jenkins)` →
  только `Docker`);
- правило containment из T6.2 («класс A ⇔ оплачиваемое покрывает `wanted`») сравнивало
  оплачиваемое с **урезанным** `wanted` и выдавало класс A там, где совпадение частичное.

### 1.2 Что сделано

Минимальное расширение существующего `Requirement`, без перестройки matcher'а:

```python
unrecognised: tuple[str, ...] = ()
disjunctive: bool = False
```

Незнакомые имена ищутся **по форме**, а не по словарю. Четыре регекспа (`_TERM_SHAPES`): `#тег`,
CamelCase, слово с цифрой, `ALL_CAPS/ALL_CAPS`. Плюс перечисление с разделителем (`_LIST_RUN`) и
`_ACRONYM` — но только как маркер списка, не как самостоятельное имя. Шум отсекает `_TERM_NOISE`
(`usa`, `ii`, `level`, `api`, …).

Отбор элемента списка (`_list_item`) принимает элемент, если он 2–30 символов, не длиннее трёх слов,
известен словарю, либо состоит из слов с заглавной буквы. **Проверка «есть слово со строчной»
выполняется ДО поиска формы** — иначе `"and Azure DevOps"` проходит целиком, потому что форма
`DevOps` находится внутри фразы. `_named_terms` дополнительно выбрасывает дубли по вложенности:
`GitLab` уступает `GitLab CI`, `CD` уступает `CI/CD`.

**Различение «A и B» / «A или B».** `_is_disjunction(text, vocabulary)` возвращает `True`, только
если «или / or / либо / either» стоит **в промежутке между соседними найденными именами**
(`gap <= 24`, без `;` и `.`). Первая версия правила («маркер между первым и последним именем»)
была слишком грубой и на реальной вакансии Python Developer давала ложное срабатывание: там `или`
соединяло другие слова, а SQL «подтверждал» PostgreSQL.

Сравнение стало зависимым от формы требования:

```python
def _answered_by(by: set[str], wanted: set[str], disjunctive: bool) -> bool:
    if not wanted:
        return True
    if disjunctive:
        return bool(wanted & by)     # «A или B» — достаточно одной альтернативы
    return wanted <= by              # «A и B» — нужны обе
```

**Класс понижается, но никогда не повышается.** Требование с незнакомыми именами уходит в C, если
хоть что-то подтверждено, и в E, если не подтверждено ничего. Понижение в E ограничено классами
A и B: для класса C это стирало бы более точную причину («частично соответствует» — это и есть
верный ответ).

**Формулировка про отсутствие навыка.** Требование спеки: «Не приписывай кандидату отсутствие
навыка». Поэтому нота читается так:

> Не подтверждено доступными фактами: «CI/CD», «GitHub Actions», «GitLab CI», «Jenkins». Этих
> названий нет в KB, поэтому справка не может ни подтвердить, ни опровергнуть их — это ограничение
> справки, а не отсутствие навыка у кандидата.

### 1.3 Про требование про регистр

Требование спеки «исправь сравнение технологий так, чтобы PostgreSQL распознавался независимо от
регистра букв» **уже выполнено** до этой работы: `_tokens` приводит текст к нижнему регистру, и
`PostgreSQL` распознаётся. Проверено замером, а не по коду. Реальный дефект был в исчезновении
незнакомых имён, и он закрыт.

При этом остаётся отдельное свойство, которое стоит помнить: `_canonical_terms_in` матчит только
цифры и ASCII (`(?<![0-9a-zа-я])…(?![0-9a-zа-я])`), поэтому `PostgreSQL` **никогда** не совпадёт с
`postgresql` внутри текста — заглавный `SQL` ломает lookbehind. «SQL сам по себе не подтверждает
PostgreSQL» выполняется по другой причине: это разные канонические записи словаря.

### 2.2 Как устроен черновик

`tools/t7_preview_adapt.py` **не является второй системой адаптации**. Он собирает уже
существующие части:

- Job-to-Candidate Brief (что вакансия просит и что кандидат может доказать);
- `master_resume.build_master_resume` (каждая строка несёт claim'ы из KB и русский рендер).

Черновик — это выбор строк master-резюме. Каждая строка либо **оставлена** как есть, либо
**переставлена**, либо **исключена**. Ни одна не переписана, поэтому выдумать факт технически
невозможно: если предложения нет в master-резюме, оно не может появиться здесь.

Выбор объявлен таблицей `SELECTION` в самом скрипте (индекс строки master → `None` / `"drop"` /
«перед индексом N»), потому что «что вынести вперёд под эту вакансию» — редакционное решение, а не
то, что следует выводить алгоритмом и потом защищать как алгоритм.

### 4.4 Что изменилось в старых тестах и почему это не подгонка
