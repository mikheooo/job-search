**Дата замера:** 2026-09-30
**Вердикт:** `FIX` — найдены три дефекта чтения, все подтверждены живьём.
**Что отправлено:** ничего. Все замеры — read-only, `SUBMIT_ALLOWED=false` в командной строке.

## 0. С чего началось

Пользователь спросил «что дальше делаем». Проверка живого состояния вместо памяти дала:

```
autonomous_cycle_runs:  messages_checked = 0  во ВСЕХ 13 прогонах
                        interviews_detected = 0 всегда
                        rejections_count    = 0 всегда
max(seen_at) в hh_message_events = 2026-09-29T07:11:34
```

То есть автономный цикл **ни разу** не прочитал переписку, а `0` в отчёте означал
не «писем не было», а «мы не смотрели». Это и есть слепота.

## 1. Дефект A: `hh-message triage` молча возвращает ноль — ✅ ИСПРАВЛЕНО

### Замер

```
HH_BROWSER_MODE=headless .venv/Scripts/python.exe ai_assistant/cli.py hh-message triage --limit 40
→ found: 0 conversations
  triaged: 0
  NEEDS_REPLY: 0 | NO_REPLY_NEEDED: 0 | HUMAN_REVIEW: 0 | ERROR: 0
  status: READ-ONLY — nothing sent.
EXIT=0
```

Против того же аккаунта, через минуту:

```
HH_BROWSER_MODE=headless .venv/Scripts/python.exe ai_assistant/cli.py message-watch --once --limit 40
→ Conversations checked: 12
  Messages seen:         12
  New incoming messages:  2
  BLOCKED / Errors:       0
```

Двенадцать диалогов против нуля. Сессия авторизована — watcher это доказал.

### Причина

Две разные дороги чтения:

| Команда | Резолвер | Мир | Проверка авторизации |
|---|---|---|---|
| `message-watch` | `_resolve_hh_evaluate` | главный фрейм | **есть** (`check_hh_session_authenticated`, fail-closed) |
| `hh-message triage` | `_resolve_chatik_evaluate` | isolated world iframe чатика | **нет** |

`_resolve_chatik_evaluate` (clī.py:3488) идёт через `make_isolated_world_evaluate`.
Когда чтение из этого мира не удаётся, ошибки нет — возвращается нулевой словарь,
и CLI печатает «found: 0 conversations». Отличить «переписок нет» от «не смогли
прочитать» по выводу **невозможно**.

Это тот же класс дефекта, что уже был признан в BLE001 finding #28 для watcher'а:
«проверка, которая не может выполниться, обязана остановить цикл». Для triage
этого не сделали.

### Доказательства
- `tools/.t728/triage_empty_20260930.txt` — ноль от triage
- `tools/.t728/watcher_once_20260930.txt` — 12 диалогов от watcher, в ту же минуту

### Фикс

FREEZE на `cli.py` снят (ответ Миши: «снимай»). Правка — пять кусков, все в
`hh_message_triage` плюс один импорт; проверено диффом против снимка
`tools/.t728/cli.py.before_T7.28A.py` — ровно 5 хунков, ничего вне пути triage.

1. **Проверка до чтения.** `check_hh_session_authenticated(...)` вызывается перед
   `fetch_hh_conversations_list_readonly`. Отказ — `RuntimeError`, который
   обрабатывается веткой `except` и печатает `BLOCKED`, а не `READ-ONLY`.
2. **Не отличить ≠ разрешено.** `verified` управляет только формулировкой:
   «not authenticated … log in» против «could not verify … fix the connection».
   Решение о блокировке принимает `authenticated` — как в watcher'е.
3. **Исключение внутри проверки — тоже блокировка.** Свой `try` вокруг гейта
   (вторая линия: первая — внутри самого `check_hh_session_authenticated`).
4. **Путь с инъекцией `evaluate_fn`** (им пользуются тесты) проверяется тоже —
   иначе логин-страница, поданная как `evaluate_fn`, читалась бы как «0 переписок».
5. **Вердикт передаётся вниз.** Владеемый путь проверяет **один раз** и передаёт
   результат в повторный вызов через `auth_verified`. Без этого повторная проба
   уходит на chatik-транспорт — см. ниже.

### Живая находка: пробу нельзя ставить в chatik-фрейм

Самая дорогая часть. Первая версия правки ставила гейт на `ev` — тот же
транспорт, которым читаются сообщения, — и **отказала здоровой сессии**:

```
BLOCKED: could not verify the HH session
  (the page returned something unrelated to the session check:
   {'error': 'chatik frame not found', 'conversation_id': None, ...})
```

Замер в одном и том же живом сеансе (`HH_BROWSER_MODE=headless`, 2026-09-30):

| Транспорт | Резолвер | `location.host` / `isTop` | Вердикт гейта |
|---|---|---|---|
| главный фрейм | `_resolve_hh_evaluate` | `hh.ru` / `true` | `authenticated=True`, `verified=True` |
| chatik-iframe | `_resolve_chatik_evaluate` | — (сторожок) | `authenticated=False`, `verified=False` |

Причина: `_resolve_chatik_evaluate` привязан к isolated world iframe'а
`chatik.hh.ru`. В этом фрейме нет навигации профиля (селекторы
`mainmenu_applicantProfile`, `mainmenu_messages`, `a[href*="/applicant/…"]` не
существуют), а при неоткрытой переписке он вообще отдаёт сторожок
`chatik frame not found`. Спрашивать у него «я авторизован?» **нельзя**.

Watcher так и не делает: `_resolve_hh_evaluate` для проверки, `_resolve_chatik_evaluate`
для чтения. `triage` имел только iframe-транспорт, потому что раньше ему второй
был не нужен.

### Тесты

### Грабли: служебный скрипт испортил переводы строк (и тесты этого не заметили)

Правка делалась байтовым патчером именно потому, что `cli.py` смешивает
терминаторы. Но скрипт **негативного контроля** (отдельная утилита) читал и
писал файл текстом — `read_text()` / `write_text()`. Текстовый режим читает
`CR CR LF` как два перевода строки и пишет обратно `CR LF CR LF`, поэтому один
круг «прочитать-записать» вставил в файл **6508 фантомных пустых строк**:

```
              CR CR LF   CR LF alone      LF     bytes
до                6437           152    6589    310145
после порчи          0         13097   13097    321482
```

**Зелёный набор тестов этого не поймал.** Пустые строки Python безразличны, AST
парсился, живой прогон работал. Поймал только прямой замер байтов — и то потому,
что номер строки в `grep` разошёлся с ожидаемым (2656 против 5231).

Почему это не косметика: проект держит два счётчика строк, и расходятся они
именно на таких файлах (`grep`/`wc` считают по `LF`, `splitlines()` и редакторы —
ещё и по голому `CR`). `docs/ble001_triage.md` объявляет систему счёта для
`cli.py`; после порчи объявленные адреса стали означать другое место. Плюс это
правка на 6508 строк в файле под FREEZE.

Исправлено восстановлением из чистого снимка и повторным наложением. В патчер
добавлен **структурный инвариант**: вставляемые строки получают терминатор файла
(`CR CR LF`), и после сборки проверяется, что счётчик вырос ровно на число
добавленных строк, иначе патчер отказывается писать:

```
ok  terminator preserved: CR CR LF 6437 -> 6557 (+120 lines added, none rewritten)
```

**Правило:** на `cli.py` — только `read_bytes` / `write_bytes` / `shutil.copy2`.
Правило «голые `\r` — только байтами» уже было в памяти проекта; наступил на него
именно потому, что писал **служебный** скрипт, а не правку.

Следствие для тестов: `inspect.getsource` на `cli.py` отдаёт удвоенные переводы
строк, поэтому проверки по исходнику обязаны нормализовать пробелы
(`" ".join(src.split())`), а не сравнивать последовательности с `\n`.

## 2. Дефект B: `sent_at` пуст в 37 событиях из 38 (97 %)

### Замер

```
2026-08-30: 28 событий, 27 с пустым sent_at
2026-09-29:  8 событий,  8 с пустым sent_at
2026-09-30:  2 событий,  2 с пустым sent_at
```

Конкретно у Agiens: `sent_at = None`, `seen_at = '2026-08-30T03:37:59'`.
Даты сообщения нет вообще. Именно поэтому «Собеседование» от 30.08 висело месяц:
по базе невозможно понять, **когда** оно пришло.

### Причина

`_CONVERSATIONS_LIST_JS` (в `hh_message_reply.py`) достаёт строки карточки в
`rawLines` и **выбрасывает** строку с датой:

```javascript
// employer-fallback filter — дата есть в rawLines, и её здесь отфильтровывают
if (!/^[0-9:]+$/.test(rawLines[i]) && !/вчера|сегодня|назад/i.test(rawLines[i]) && rawLines[i].length < 60) {
    employer = rawLines[i];
    break;
}
```

Дата нужна как **фильтр**, но она же — данные. Её следовало бы прочитать, а не
отбросить. Дальше по цепочке ветка сниппета в `hh_message_watcher.py` вообще
**зашивает `sent_at=None`** жёстко (`sent_at=None,` рядом с
`dialog_msgs.append(HHMessage(message_id="m0", ...))`), и в БД попадает пусто.

### Живой замер форматов (tools/.t728/probe_card_lines.py)

Строка `[1]` каждой из 12 карточек:

```

'вчера'  → 5662692999  Академия Йоги
'пн'     → 5662603940  EvaTeam
'пн'     → 5664349328  Каналсервис
'пн'     → 5664348392  АФЛТ-Системс
'вс'     → 5662695512  ЮК Опора
'ср'     → 5566499616  ТопБухгалтер

**Два формата:** относительный (`вчера`, `пн`, `вс`, `ср`) и абсолютный (`ДД.ММ`).
Оба несут смысл, оба теряются.

### Ключевой факт для фикса: дата ВСЕГДА на индексе 1

Проверено по всем 12 карточкам: `rawLines[0]` — заголовок вакансии,
`rawLines[1]` — **дата**, `rawLines[2]` — работодатель, `rawLines[3]` — текст,
`rawLines[4]` — счётчик непрочитанного (если есть).

```
[0] keep   'Специалист технической поддержки / IT-ассистент (IT Support…'
[1] DROP   'вчера'                        <-- ЭТО ДАТА, позиция стабильна
[2] keep   'Кадровое агентство Dream Team'
[3] keep   'Отказ'
[4] DROP   '1'
```

То есть фикс не требует эвристик: `rawLines[1]` — дата во всех 12 случаях без
исключений. Остаётся только разобрать два формата в нормальную дату.

### 2.1 Фикс B — что именно сделано

**Идентичность отделена от показа.** Это главное решение, и оно же — то место,
где я ошибся первым заходом (см. 2.2).

* `hh_message_reply.py` — добавлен `parse_card_date(raw, today)` (чистый stdlib):
  разбирает `вчера`, `пн`…`вс` и `ДД.ММ` / `Д.ММ` в `datetime` с точностью до
  **суток**. День недели разрешается в ближайший **прошедший** день, включая
  сегодня (`(base.weekday() - target) % 7`), поэтому `ср`, прочитанное в среду,
  не уезжает на неделю назад и никогда не даёт будущую дату.
* `_CONVERSATIONS_LIST_JS` — добавлено поле `last_message_date_raw` (строка 1
  карточки), при этом строка из `rawLines` **не удалена**.
* `hh_message_watcher.py` — дата кладётся в `sent_at` через `card_dates`, а
  `compute_message_fingerprint` **не тронут**.

Ключевое свойство: **значение с карточки не попадает в fingerprint.** `sent_at`
остаётся `""` на пути сниппета, а разобранная дата идёт отдельным полем. Если бы
`вчера` попало в ключ, то каждый следующий день читалось бы как «позавчера»,
fingerprint менялся бы на границе суток, и один и тот же отказ выглядел бы новым
событием — с дублем строки и, при живом цикле, с дублем реакции.

### 2.2 Ошибка, которую я совершил и откатил

Первым заходом я **предположил**, что ключ дедупа — `conversation_id + sender +
text`, и выкинул `sent_at` из payload. Написанный мной тест это «подтвердил» —
потому что кодировал то же предположение. Разоблачил ошибку только реверс-инжиниринг
всех 38 строк БД: реальный ключ — четыре поля, и с пустым `sent_at` он
воспроизводится **38 из 38**. Правка откачена целиком.

Урок записан прямо в тестовый файл: **проходящий тест, закрепляющий твою гипотезу,
не доказывает ничего.** Здесь он был хуже падающего.

### 2.3 Живой прогон и дозапись уже накопленных строк

Замер `tools/.t728/dates_live_20260930.txt`: **разобрано дат 12 из 12**, ни один
работодатель не подменён датой.

Дефект B закрыт для **вновь обнаруживаемых** сообщений. Но правка watcher'а
срабатывает только в момент обнаружения, поэтому 37 уже лежавших строк остались
пустыми. Для них сделан отдельный, явно помеченный шаг —
`tools/.t728/backfill_sent_at.py` + `db.backfill_hh_message_sent_at(...)`.

Что важно в устройстве дозаписи:

* Это **UPDATE, а не INSERT** — дозапись физически не может создать событие,
  которого на странице нет.
* Условие `AND (sent_at IS NULL OR sent_at = '')` — уже известное время не
  перебивается. Настоящая метка точнее даты с карточки, и затирать её нельзя.
* Пишется ровно один столбец; `message_fingerprint` не пересчитывается.

Измерение (`tools/.t728/backfill_feasibility_20260930.txt`): из 37 пустых строк
замером закрываются **10**, остальные 27 — переписки вне замера (15 из них —
`neg_*`, переговоры со страницы вакансии). Даты для них взять неоткуда, и
**выдумывать её нельзя**: пустое поле честнее неверной даты.

```
до:      с датой  1 из 38
после:   с датой 11 из 38   (изменено 10, повторный прогон — 0)
```

Сквозная проверка после записи: живой цикл `message-watch --once --limit 40`
даёт `Already processed: 10`, `New incoming messages: 0`, `BLOCKED / Errors: 0`,
`REPLY SENT: NO (0)`. Это и есть доказательство, что дозапись не воскресила дедуп:
если бы ключ изменился, цикл увидел бы 10 «новых» отказов.

## 3. Дефект C: дата подставляется как имя работодателя — ✅ ИСПРАВЛЕНО

**Важно: этот дефект я сначала объявил активным, потом латентным, и вторая оценка
тоже была неточной.** Он не срабатывает *сегодня* — но не «по удаче», а потому что
работает ровно один селектор. Разбор ниже.

Фильтр в `_CONVERSATIONS_LIST_JS` ловил только `вчера|сегодня|назад`,
но **не** ловил `пн`, `вс`, `20.09`. Если бы до этой ветки доходило, первая же
неподходящая строка стала бы `employer`.

### Воспроизведение на живых строках (синтетический прогон прод-логики)

| Карточка | Настоящий работодатель | Что извлёк бы прод как `employer` |
|---|---|---|
| Dream Team | Кадровое агентство Dream Team | ✅ верно (спасло ровно то, что `вчера` отфильтровано) |
| Скайтек | Скайтек | ❌ **`20.09`** |
| EvaTeam | EvaTeam | ❌ **`пн`** |

### Но на живой странице это не срабатывает

Замер `subFound` (найден ли `[data-qa*="subtitle"]`) по всем 12 карточкам:

```
cid          | subtitle найден? | subText                        | line1
-------------|------------------|--------------------------------|----------
5665125042   | True             | Кадровое агентство Dream Team  | 'вчера'
5662692999   | True             | Академия Йоги                  | 'вчера'
5662603940   | True             | EvaTeam                        | 'пн'

`subtitle` находится **всегда** (12/12) и **всегда** содержит верного работодателя.

| Сверка | Результат |
|---|---|
| `employer` в БД vs живая карточка | **0 расхождений из 10** |

### Уточнение задним числом: масштаб не «латентный по удаче»

Формулировка «латентный» выше верна по механизму, но **вводит в заблуждение по
масштабу**, и измерение это показало. Негативный контроль
(`tools/.t728/filter_harness.js` со старым правилом, замер 2026-09-30):

```
старое правило /^(вчера|сегодня|позавчера|назад)$/ ⇒
дата стала работодателем в 10 карточках из 12:
  пн (3), вс (1), ср (1), 20.09 (2), 15.09 (2), 12.09 (1)
выжили ровно те 2, где HH напечатал 'вчера' — единственная форма, которую
старый фильтр знал
```

То есть защищало нас **не правило, а селектор**: одна строчка DOM, три
гадательных селектора `[data-qa*="subtitle"], [class*="subtitle"],
[class*="employer"]`. Правило же пропускало 10 форм из 12. «Латентный» здесь
означает «не сработал сегодня», а не «сработал бы редко».

### Фикс

Правило вынесено в **одну** константу `CARD_DATE_LINE_JS_PATTERN` в Python и
подставлено в **оба** фильтра (`employer` и `snippet`) вместо литералов:

```python
CARD_DATE_LINE_JS_PATTERN = (
    r"^(?:вчера|сегодня|позавчера"
    r"|пн|вт|ср|чт|пт|сб|вс"
    r"|\d{1,2}\.\d{1,2})$"
)
```

Два решения, которые стоит объяснить:

* **Почему регулярка живёт в Python, а не набрана в JS дважды.** JS-строка не
  исполняется ни одним тестом — нужен живой браузер. Правило, записанное только
  в ней, проверить нечем: именно поэтому дефект C дожил до T7.28, хотя тест
  «дата не путается с работодателем» существовал. Он проверял `parse_card_date`
  (парсер), а не фильтр. Это разные вещи, и вторая не проверялась вообще.
* **Почему подстановка, а не f-строка.** JS содержит `{}`; f-строка их съест.
  Использована `.replace("__CARD_DATE_LINE__", ...)` с проверкой, что
  плейсхолдеров ровно два (см. тест) — три означало бы, что правило записано
  где-то ещё и разъедется, одно — что второй фильтр остался со старым.

**Проверка, которая ловит именно этот класс.** `tools/.t728/filter_harness.js`
исполняет **не пересказ** логики, а её дословную копию (сверяется тестом),
на **живых** строках 12 карточек в боевом сценарии «`subtitleEl` не совпал»:

```
OK: 12 карточек, дата не стала ни работодателем, ни сниппетом
```

и с откаченным правилом — `ПРОВАЛ: 10 нарушений`. Harness — единственное место,
где дефект C проверяется на настоящих данных.

Сквозная проверка живьём после правки: `Conversations checked: 12`,
`Already processed: 10`, `New: 0`, `BLOCKED: 0` — изменённый JS читается
настоящей страницей и не ломает чтение.

Это снимает и вопрос про `Алф маркет` в исходном виде: там `sender='employer'`
на нашем собственном тексте — но это уже дефект направления (сниппет-ветка
watcher.py:380), а не имени работодателя. Он подтверждён и остаётся открытым.

## 4. Что ещё вскрылось попутно

### 4.1 База — три снимка, а не история

```
2026-08-30:  28 событий (20 в ОДНУ секунду) — разовая заливка
2026-09-29:   8 событий
2026-09-30:   2 событий
```

30.08 — это батч (20 событий с `seen_at` одной секунды), а не цикл опроса.
Между 30.08 и 29.09 — **месяц пустоты**. Ровно то, что показывают нули
`messages_checked`.

### 4.2 «Статус: …» — это системные ярлыки, а не письма

В заливке 30.08 смешаны две разные вещи:

- 20 событий вида `'Статус: Собеседование'`, `'Статус: Отказ'`, `'Статус: Не просмотрен'` —
  это **системные метки HH**, а не сообщения работодателя;
- 8 событий — реальные письма.

Все 20 ярлыков лежат со `status='NEEDS_HUMAN_REVIEW'`, то есть каждый из них
поднимает флаг «нужен человек». 18 из 20 — ложные (это просто «не просмотрен»).

### 4.3 Agiens — две разные переписки, и память помнит только одну

| conversation_id | Что | Статус в БД |
|---|---|---|
| `neg_136745031` | `'Статус: Собеседование'` | `NEEDS_HUMAN_REVIEW` |
| `5585084830` | `'Собеседование'` (живое письмо) | `NEEDS_HUMAN_REVIEW` |

В памяти проекта Agiens `136745031` записан как `WITHDRAWN`. Вторая переписка
(`5585084830`) — с другим `conversation_id`, о ней записи нет вообще.
Оба висят с 30.08 на гейте `sensitive_topic_requires_human_decision`
(`hh_application_orchestrator.py:711`, срабатывает при `cls == "HUMAN_REVIEW"`).
Это **гейт «решает человек», а не ошибка** — и он держит месяц.
