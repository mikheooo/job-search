## T6/T7 Job-to-Candidate Brief (`ai_assistant/candidate/job_brief.py`)

`python -m ai_assistant.cli candidate-job-brief --vacancy <stable_id> [--details|--json] [--out PATH]`;

**Устройство, которое нельзя ломать:** **класс A достижим только через `duty`** — в KB `role_id` несут
лишь `duty`-факты, `skill` несёт `parent_id` → группу навыков; голый `skill` = класс D, проектный факт =
B и в A не поднимается (**на этом стоит честность модуля**). **Статусы фактов после загрузки из JSON —
`str`, не `ClaimStatus`:** `==` работает, `is` даёт молчаливый ноль; читать через `kb.by_status()`.
**`get_vacancy_by_id` отдаёт позиционный кортеж** (`get_connection` не ставит `row_factory`) —
оборачивать в `db._row_to_vacancy(row)`. Описания вакансий в `state.db` — **одна строка без `\n`**; у
habrcareer это огрызок из хэштегов. Порядок доказательств зависит от класса (A ведёт оплачиваемым, B —
проектом), короткий вид печатает две строки, поэтому **порядок = смысл**.
`remote_filter.classify_work_format` намеренно отвергает «Можно удалённо».

**T6.1:** KB называет проект ДВУМЯ идентификаторами — `project_status.parent_id` → claim_id, а
`evidence["project_id"]` → нормализованный слаг (`repiton`); резолвер принимает обе формы, запасное имя —
«свой проект», **никогда** сырой идентификатор. Оплачиваемое и своё различаются свойствами, а не
строками: `Assessment.commercial_evidence` / `.project_evidence` / `.resume_evidence` (первое содержит и

каноническим именам** (`bitrix24`), не по тексту: русская вакансия пишет `#Битрикс24`.

**Ловушка:** span «…experience: » съедает пробел-разделитель, замена обязана его вернуть. **Ловушка:**

**T7 ч.1 — неизвестное название не исчезает из требования.** Причина дефекта: извлечение требований
опиралось только на словарь технологий кандидата, поэтому незнакомое имя пропадало и частичное
совпадение читалось как полное. Минимальное расширение `Requirement`: поля `unrecognised` и
`disjunctive`. Имена ищутся **формой**, а не словарём (`_TERM_SHAPES` — `#тег`, CamelCase, слово с
цифрой, `ALL_CAPS/ALL_CAPS`; `_LIST_RUN`; `_ACRONYM` только как маркер; `_TERM_NOISE`). В `_list_item`
**проверка «есть слово со строчной» идёт ДО поиска формы**, иначе `"and Azure DevOps"` проходит целиком;
`_named_terms` выбрасывает `_is_part_of`-дубли (GitLab уступает GitLab CI). **`_is_disjunction` требует,
чтобы «или/or/либо» стояло в промежутке между СОСЕДНИМИ найденными именами** (`gap <= 24`, без `;` и
`.`) — маркер «между первым и последним» слишком груб: на реальной вакансии Python Developer `или`
соединяло другие слова, и SQL подтверждал PostgreSQL. `_answered_by`: для «A и B» нужно `wanted <= by`,
для «A или B» достаточно `wanted & by`. Незнакомое имя сохраняется и печатается нотой «Не подтверждено
доступными фактами: … Этих названий нет в KB, поэтому справка не может ни подтвердить, ни опровергнуть
их — это ограничение справки, а не отсутствие навыка у кандидата» (**никогда не читать как отсутствие
навыка**). Класс понижается, но **никогда не повышается**; переопределение в `E_UNCONFIRMED` ограничено
классами A/B — для C это стирало более точную причину. Замер: по пяти вакансиям двигаются 4 требования,
все A/B → C. Тесты 99 → 135. Разборы: `tools/.t7_class_diff.py`, `tools/.t7_terms_probe.py`.

**T7 preview** (`tools/t7_preview_adapt.py`) — черновик под одну вакансию, собранный **из строк
master-резюме**, не написанный заново; выбор строк объявлен таблицей `SELECTION` (индекс → keep /
`"drop"` / «перед индексом N»). Три места, где легко ошибиться: (1) строку навыков **нельзя** узнавать по
«буллет, начинающийся с `- **`» — под это попадает и строка образования; признак — секция

«участник ↔ claim» там не однозначно; (3) `render_markdown(lang="ru")` гонит **каждую** строку с

## Отчёт `docs/ble001_triage.md` и ратчет ссылок

Все `файл.py:NNNN` — в системе счёта `grep -n` (маркер `<!-- line-numbering: grep -->`). После правки:
`.venv/Scripts/python.exe tools/report_line_refs.py` (ворота, 0 за концом файла) и `--symbols`
(советующий список, ратчет ≤ 18). **Любое число — из только что сделанного прогона.** **Состояние:
ратчет красный (24 при 18) и был красным ДО работы T1–T6.1.** Базис **мерить**: «HEAD-отчёт + HEAD-код» =
277/164/**24**; «текущий отчёт + текущий код» = 301/177/**24**. Порог **не поднимать**. **Промежуточное
«новый отчёт × старые источники» атрибуцией НЕ является** (дало 39) — считать только состояние × своё
состояние. **Отметка чаще означает имя не на той строке, а не лишний адрес:** на строке с адресом
назвать символ, который там **есть**; имя, которого там нет, убрать со строки адреса. **`QUOTED` лечит
только ворота «вне диапазона».** **Раздел может описать свою же ошибку и получить за неё отметку**
(№65). **У советующего режима слепое пятно:** ссылка на строке без имён символов не проверяется вообще.
**Правка источника сдвигает ссылки отчёта в него самого** — смещение считать по `grep -n` самого
символа, не арифметикой; **исторические ссылки НЕ переводить**; **не писать исправленный адрес в форме
`file.py:NNNN`** в тексте «раньше было так» — счётчик читает его как живую ссылку. Скрипт-правку писать
**идемпотентной**: инструмент иногда выполняет команду дважды, и второй прогон падает на
`assert count == 1` — читается как «не применилось». **«Чистый CRLF» проверять равенством
`CRLF == число строк`.** **Дельту правки считать ДО записи.** **Якорь вставки должен быть уникальным,
место проверять ПОСЛЕ**; **перевод ссылок делать ДО вставки раздела, который этот перевод записывает.**

## Инструменты (`tools/`) и окружение

**`tools/` НЕ в `.gitignore`** — инструменты коммитятся; игнорируются только `.pytest_*.xml`. **Прибор,
меняющий файлы, обязан иметь три вещи:** (1) калиброванные хеши (`EXPECTED_SHA`); (2) замок, снимаемый
ядром (`msvcrt.locking` на `%TEMP%\job-search-mutation.lock`; файл замка **не удалять никогда**);
(3) восстановление из сохранённых байтов и сверка с **калиброванным** хешем, а не с прочитанным.
Причина: команда может выполниться дважды, и два экземпляра, сохранив «оригиналом» уже подменённые байты,
оставят дерево чужим, печатая `restored: True` (так 2026-09-20 потерялась строка в
`submission_recovery.py`). **Сводка прибора не смеет врать.** **Критерий «мутация поймана» — `any()`, а
не `all()`**; пин, отсутствующий в отчёте прогона, — `UNKNOWN`, а не `PASS`; итог читать тремя строками:
`verdict`, `evidence`, `controls` (все `PASS`). **Мутационные инструменты после каждой правки исходника
перезапускать** — якорь протухает молча, и «не применилась» неотличимо от «выжила»; различать `ABORTED`
и `SURVIVED`. **Размах новой проверки мерить на КОПИИ боевой базы** (`config.DB_FILE` на копию до
импорта).

**`git show <sha>:<путь> | sha256sum` может повиснуть** — хеш блоба брать через `git cat-file blob
<sha>:<путь>` из Python + `hashlib`. `git status --cached` не существует. **`git cat-file blob` отдаёт
LF-нормализованный текст** (дерево CRLF, блоб LF): число LF равно `grep`-числу дерева, но байты
сравнивать нельзя. **В git-командах из этой оболочки не работают записи в refs с поддиректорией:**
`git fetch`/`git push` удаляют `.git/refs/remotes/origin/<branch>` и не создают заново. **Хеш
артефактов сравнивать в текстовом виде** — `Path.write_text` на Windows пишет CRLF, рендер даёт LF, и
`sha256(read_bytes())` не сойдётся при нулевом diff; нормализовать `raw.replace(b"\r\n", b"\n")`.

## Стиль правок

Сначала пины, потом правка: красный прогон пинов = замер дыры. **Один `Edit` на файл за раз**; после

## T7.1 — редакционная адаптация (2026-09-24)

Инструмент один: `tools/t7_preview_adapt.py` (~1560 строк). В T7 он только удалял строки; в T7.1
добавлены объявленные операции, потому что адаптация должна быть редакционной:

- `Rewrite(text, reason, claims=(), without=())` — новая формулировка; `claims` берутся из master,
  `without` — что выброшено.
- `Merge(sources, text, reason)` — **claim-множество объединённой строки считает сам инструмент**,
  поэтому слияние не может потерять claim.
- `Addition(after, kind, text, claims, reason)` — строки в master нет; claim'ы обязаны быть
  master-овскими.

Механика: `forgotten = set(by_index) - declared` ⇒ `SystemExit` («профиль не описывает строки
master-резюме»); объявленная подстрока проверяется на существование в строке; `skills_order`
переставляет **только буллеты** (`kind == "bullet"`), иначе в список попадает заголовок
`## CORE SKILLS`; добавления с общим якорем сохраняют объявленный порядок. Профиль, объявивший
`drop_reasons`, обязан объявить причину **для каждого** исключения — иначе exit; старый профиль
T7 preview оставлен на `_legacy_drop_reason`.

Ловушки, на которых уже спотыкались:
- строку навыков **нельзя** узнавать по «буллет, начинающийся с `- **`» — под это попадает строка
  образования; признак — секция `## CORE SKILLS`;
- добавление, привязанное к строке, которую ход переместил, встаёт не туда (Speedcast уехал выше
  буллетов Avantis) — привязывать к той строке, что окажется выше;

### `Confirmed` — что это и чего в нём нет

`Addition` стоит на claim'е master-резюме, и claim проверяется. У строки, которую KB не
держит, проверять нечего, и выдавать её за подтверждённую нельзя. `Confirmed` проверяет три
**учётных** свойства: строка объявлена в профиле; объявление называет, **кто и когда**
подтвердил (пустой источник — ошибка сборки); строка **дошла до отрендеренного черновика**.
Последнее не декоративно: подтверждённая строка, молча потерянная при сборке, выглядит ровно
как строка, которую никто не подтверждал.

У подтверждённых строк **намеренно нет claim'ов** (`mr.Line(..., ())`). В `source_map.md` они
в отдельном разделе «Объявлено кандидатом (источника в репозитории нет)» — не в «Строках без
claim'ов», где написано, что это оформление.

### Пагинация DOCX — `keepNext` в самом документе

записи Speedcast. Лечится свойствами OOXML, а не шрифтом:

- `w:keepLines` — на **всех** абзацах (45 из 45): абзац не рвать между страницами;
- `w:keepNext` — на **32**, то есть на каждом абзаце записи, кроме последнего: Word тогда переносит
  запись целиком. Если запись выше страницы, Word `keepNext` игнорирует — **правильное направление

**`w:pPr` — последовательность, не множество.** Порядок обязателен: `keepNext`, `keepLines`, `numPr`,
`pBdr`, `spacing`, `jc`. `w:numPr` после `w:spacing` валидирующий читатель отвергает. Порядок задан
явно в `_docx_para`.

**Одна группировка на два формата.** `sections(blocks)` делит тело на разделы (`##`) и записи (`###`);
её используют и `to_html` (Chrome → PDF), и `build_docx` (OOXML). Поэтому швы одни — но ломаются
форматы в **разных местах** (PDF после Speedcast, DOCX перед ним): движки разные. Оба разрыва
допустимы, потому что ни одна запись не разрезана.

`release()` останавливает браузер только при `remaining_operations == 0`; `stop_browser=False`
пишет в отчёт `"browser left running with no operation"`. Когда сессия передана, закрываются
**её** вкладки; когда нет — релиз **не** пишет `tabs_closed: 0`, а перечисляет вкладки эндпоинта
(`tabs_seen_on_endpoint`) и называет число.

`acquire()` → `ACQUIRED` / `REUSED` / `BUSY`; `hh_operation()` поднимает `BrowserBusy` (HTTP 409).
`release_owner(owner_type)` отказывается трогать чужой lease.

### Грабли

- **`stdout` в Windows переводит `\n`→`\r\n`.** При восстановлении файла «байт в байт» писать через
  `sys.stdout.buffer.write(text.encode("utf-8"))`, иначе хеш не сойдётся: у меня разошлось ровно на
  +484 B — по одному `\r` на каждую из 484 строк.
- **A/B по восстановленному файлу — дешёвый строгий способ отличить свою регрессию от чужой.**
  Обратный патч двух правок + сверка sha256 с известным `156bf29a…` (сошлось побайтово) ⇒ падение
  воспроизводится на домиграционном файле ⇒ регрессия чужая. Без этого пришлось бы спорить.
- **Мок по идентичности строки не проверяет селектор.** `_FakeSession.evaluate_on` возвращал карточки
  при `expression == ro.READ_CARDS_JS` — а устаревший селектор объект как раз и сохраняет. Отсюда
  DOM-тест на реальном браузере.
- **`git show :path` в этой оболочке не сработал** (exit 128) ⇒ версию «до» брать не из индекса, а
  восстанавливать обратным патчем.
