## Честная оценка

**Это не катастрофа и не «всё тормозит».** 0.76 с на прогон — терпимо.

Проблема в другом:

1. **Растёт линейно.** Граф показал 268 связей неделю назад, 345 сейчас. Каждый новый
   модуль добавляет вызовы. Через полгода это будут другие цифры.
2. **25 вызовов внутри самого `db.py`** — каждый `save_*` / `get_*` прогоняет DDL.
   Это горячий путь, и он весь в этом мусоре.
3. **Два `ALTER TABLE` в try/except** кидают и ловят `OperationalError` на каждом вызове.
   Работает, но это костыль, оставшийся от старой версии схемы.
4. **`init_db()` используют как пробу доступности БД** — в `get_production_health()`
   (строка ~2584). Там нужен `SELECT 1`, а не 84 DDL-оператора.
5. **486 строк DDL в файле с бизнес-логикой** — это главная беда. Читать `db.py` тяжело,
   править схему страшно.

## План

### Шаг 1. Вынести DDL в `ai_assistant/schema.py`

Перенести строки 28–513 из `db.py` в новый модуль. Одна функция:

```python
def apply_schema(conn: sqlite3.Connection) -> None:
    """Идемпотентно накатывает схему. Вызывать один раз на процесс."""
```

Что даёт: `db.py` худеет с 3225 до ~2740 строк, DDL лежит отдельно и его не страшно править.

### Шаг 2. Версионный гейт вместо «выполнять всегда»

Вместо того чтобы гонять 84 оператора на каждый вызов, запоминать, что схема уже накатилась.

```python
_SCHEMA_SQL = open(...)  # или константа
SCHEMA_FINGERPRINT = hashlib.sha256(_SCHEMA_SQL.encode()).hexdigest()[:16]

def ensure_schema() -> None:
    conn = get_connection()
    try:
        cur = conn.execute(
            "SELECT fingerprint FROM _schema_meta WHERE id = 1"
        )
        row = cur.fetchone()
        if row and row[0] == SCHEMA_FINGERPRINT:
            return  # схема актуальна, выходим за микросекунды
        apply_schema(conn)
        conn.execute(
            "INSERT OR REPLACE INTO _schema_meta (id, fingerprint, applied_at) "
            "VALUES (1, ?, ?)", (SCHEMA_FINGERPRINT, now_iso())
        )
        conn.commit()
    finally:
        conn.close()

def init_db() -> None:
    """Оставлено для обратной совместимости. Все 143 вызова продолжают работать."""
    ensure_schema()
```

**Почему fingerprint, а не номер версии.** Номер версии надо не забыть поднять — и рано
или поздно забудут, после чего новая таблица молча не создастся. Хэш от текста схемы
снимает эту обязанность: поменял DDL → хэш изменился → схема переприменилась сама.

### Шаг 3. ALTER TABLE — **пересмотрено, НЕ делать как планировалось**

Исходный план предлагал убрать try/except вокруг двух `ALTER TABLE application_queue`.
**Это было ошибкой в плане, и вот почему.**

`CREATE TABLE IF NOT EXISTS application_queue` сразу создаёт таблицу с колонками
`canonical_id` и `representative_vacancy_stable_id`. Но на базе, созданной старой версией
кода, этих колонок нет — и `ALTER TABLE` их добавляет. Убери try/except — и на старой базе
получишь `sqlite3.OperationalError: duplicate column name` при каждом запуске.

**Решение: оставить как есть.** С версионным гейтом `ALTER` выполняется максимум один раз
на версию схемы, поэтому стоимость исключения уже не имеет значения. Перенос выполнен
байт в байт, включая try/except.

### Шаг 4. Починить пробу доступности — **сделано, но не так, как планировалось**

Исходный план предлагал заменить `init_db()` на `SELECT 1`. **Ещё одна ошибка в плане.**

`init_db()` в `get_production_health()` делала две вещи, а не одну: проверяла доступность
**и гарантировала, что таблицы существуют** — ниже по функции идут запросы к
`telegram_delivery_records` и другим таблицам. Убери её совсем — на свежей базе
health-check упадёт на первом же запросе.

Сделано так:

```python
try:
    ensure_schema()          # схема нужна для запросов ниже; стоит ~0.5 мс
    conn = get_connection()
    cur = conn.cursor()
    cur.execute("SELECT 1")  # настоящая проба: sqlite3.connect ленивый
    health_result["db_accessible"] = True
except Exception as db_err:
    ...
```

`SELECT 1` здесь не избыточен: `sqlite3.connect()` ленивый и на отсутствующий файл
не ругается, так что без явного запроса доступность не проверить.

## Риски и как их закрыть

| Риск | Как закрыть |
|---|---|
| Забыли поднять версию — новая таблица не создалась | Не актуально: fingerprint считается от текста схемы, поднимать ничего не надо |
| Гейт сломается — схема перестанет накатываться на новой базе | Тест: создать пустую БД, вызвать `ensure_schema()`, проверить что все 25 таблиц на месте |
| 143 вызова сломаются при переименовании | Не переименовывать: оставить `init_db()` как тонкую обёртку. Чистить вызовы потом, по желанию |
| Тесты (179 вызовов) завязаны на побочные эффекты init_db | Тесты трогать не надо — обёртка сохраняет поведение |

## Что делать НЕ надо

- **Не трогать сами DDL-тексты.** Переносить как есть, буква в букву. Любая правка схемы —
  отдельная задача с отдельным тестом.
- **Не вычищать 143 вызова в том же коммите.** Они станут бесплатными после шага 2.
  Чистка — отдельный, чисто косметический проход.
- **Не трогать `state.db`.** Есть бэкапы `state.db.pre-stabilization-*`, но они не понадобятся:
  все операции идемпотентны, `init_db` не содержит INSERT / UPDATE / DELETE / DROP.

## Порядок

1. Шаг 1 + шаг 2 вместе — один коммит, механический перенос.
2. Прогнать тесты.
3. Шаг 3 и 4 — вторым коммитом.
4. Обновить граф: `gf.py update .`

Ожидаемый итог: 143 × 5.3 мс → ~0, `db.py` минус 486 строк.
