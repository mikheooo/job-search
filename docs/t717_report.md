### G.2 Ошибка, которую я допустил и починил

`set_application_status()` **сам** вставляет строку истории при создании — create-ветка,
`application_tracking.py:197-204`. Я этого не увидел (читал файл до строки 195) и вставил строку

ровно одна строка — **1814**.

**Урок:** комментарий на строке 195 («we will create history via separate insert if needed»)

не «только запись строки», он же и историк при создании.

### G.3 Вторая потеря и её восстановление

`set_application_status()` обновляет заметку через `COALESCE(?, notes)`, то есть **непустая**
новая заметка **затирает** старую. У строки ОПОРЫ была reconciliation-заметка T7.15: время отклика,
`negotiation 5606962176`, `chat 5662695512`, `resume 287960707`, sha письма. Сами данные не
потеряны — они лежат в `application_submissions.submission_json`, — но человекочитаемая строка из
`application_tracking` ушла. Восстановил слиянием: `notes` = новая заметка + хвост
`--- Original reconciliation note (preserved): <старая>`, 589 → **835** символов. Правил **только
поле `notes`** прямым `UPDATE`, а не повторным вызовом `set_application_status`, чтобы не сдвинуть
`last_status_change_at` (он бампается даже при неизменном статусе — это описано в докстринге
самого модуля).
