## 2. OUTBOUND HISTORY — из чего собрана

Инструмент `tools/.t91/fresh_queue.py` → `load_db_history()`. Каждая запись несёт девять полей:
`source, source_id, canonical_url, company/client, role, action_type, action_time, status, evidence`.

| источник | что даёт | записей |
|---|---|---|
| `application_tracking` | место заявки в цикле (`APPLIED`, `SUBMITTED`, `READY_TO_APPLY`, `WITHDRAWN`, `REJECTED`) | 1794 |
| `hh_application_transitions` | **факт отправки**, независимо от остальных таблиц | 56 |
| `application_submissions` | исход одной попытки отправки | 21 |
| `application_reviews` | решения по пакетам | 20 |
| `application_packages` | **подготовленный** пакет = черновик, не контакт | 35 |
| `hh_applications` | состояние отклика (`READY_TO_SUBMIT` = черновик) | 20 |
| `hh_message_events` | переписка с работодателем | 38 |
| `telegram_delivery_records` | доставленные дайджесты | 58 |
| публичные посты n8n Community | **комментарий в треде = контакт** | 106 |

**Главное измерение, ради которого всё это:** источники **противоречат друг другу**, и
одно-табличный чекер обязательно врёт. Пример: `hh:136551280` — в `hh_application_transitions`
есть `SUBMITTED` с причиной `controlled_runner_submit_confirmed`, при этом в
`application_submissions` строки `SUBMITTED` **нет**, а в `application_tracking` строки **нет
вообще**. Читатель одной таблицы назовёт отправленный отклик неотправленным — и отправит второй
раз. Поэтому история собирается из всех источников сразу, и статус берётся по **самому сильному**
событию.

**`READY_TO_SUBMIT` — это черновик, а не контакт** (`draft_approved_ready_for_confirmed_send`).
`application_packages` — подготовленный пакет. Считать любое из них контактом = молча выбросить
живую возможность; считать отправленное черновиком = отправить второй раз. Обе ошибки дорогие,
поэтому `DRAFT_ONLY` — отдельный статус (контроль N5).

## 3. Каноническая идентичность возможности

Одна и та же возможность живёт на двух досках, под разными URL, как перепост, как тред на форуме,
как строка в БД **и** как живой URL. Считать её двумя возможностями = показать Мише пять строк,
за которыми три работодателя.

`canonical_key()` (`fresh_queue.py`) сворачивает hh / n8n-тред / reddit / remoteok / wwr / habr /
himalayas / arc по стабильному id источника и каноническому URL. Отдельно `mirror_key()` в
`fresh_top.py` ловит зеркала по `нормализованная компания + нормализованная роль`.

**Схлопнуто зеркало: 1** — `wwr:sticker-mule-ai-agent-engineer` ≡ `remoteok:1137399`
(одна компания, одна роль: `stickermule|aiagentengineer`). Оставлена строка remoteok как
первоисточник. Контроль N3.

**Две ошибки нормализации, найденные здесь же:**

1. `norm_company` с `[^a-z0-9]` **вытирал кириллицу в пустоту**: «Новабев Инфо Тех» и
   «ООО Энергобезопасность» обе становились пустой строкой, и два **разных** работодателя с
   одинаковым типовым заголовком схлопывались как «зеркало». Починено сохранением
   `\u0400-\u04ff` и снятием `\b(ооо|оао|зао|ип|пао)\b`.
2. Дедупликация **по одному работодателю** — иначе два офиса одной компании занимают две строки
   TOP-5. Это правило, а не баг: оно задокументировано в §7.

| статус | что значит | в прогоне |
|---|---|---|
| `NEVER_CONTACTED` | ни одного исходящего события к этому работодателю | **57** |
| `DRAFT_ONLY` | пакет подготовлен, но не отправлен | 5 |
| `CONTACTED` | публичный комментарий / сообщение, ответа нет | 14 |
| `APPLIED` | отклик отмечен в трекинге | 2 |
| `SUBMITTED` | отправка подтверждена (`hh_application_transitions`) | 4 |
| `REJECTED` | работодатель прислал отказ | 2 |
| `FOLLOW_UP_DUE` | контакт был, но ответа нет и срок назрел | *решение очереди follow-up, §8* |
| `CLOSED` | работодатель сам сказал «больше не нанимаем» | 2 (в follow-up) |
| `UNKNOWN_HISTORY` | **прочитать историю невозможно** | 6 |

**`UNKNOWN_HISTORY` — не «не контактировали».** Шесть строк — это Reddit-лиды: у Reddit нет
публичного API, по которому можно доказать, писал ли Миша автору в личку. Отправить такую строку
в APPLY NOW = риск послать второе сообщение человеку, с которым уже говорили. Поэтому они
**исключены** из свежей очереди, а не переведены в `NEVER_CONTACTED`.

**Ловушка, найденная здесь же:** определение Reddit шло по `source == "reddit"`, но все
засеянные строки несут `source='vacancies_json'` — **какая бы доска ни была источником**. То есть
проверка по имени источника молча пропускала **каждый** Reddit-лид. Починено определением по URL
(`reddit.com` в ссылке или `reddit:` в ключе).

## 6. Страница, тред и роль — три разные вещи

T9 складывал всё в один флаг и получал противоречие: `verified_role_open = true` при
`ROLE STATUS: NOT VERIFIED`. T9.1 разводит три измерения.

| измерение | вопрос | значения |
|---|---|---|
| `page_status` | страница отвечает? | `PAGE_LIVE` / `PAGE_UNVERIFIED` / `PAGE_GONE` |
| `thread_status` | тред на форуме активен? | `THREAD_ACTIVE` / `THREAD_QUIET` / `THREAD_DEAD` |
| `role_status` | **роль действительно открыта?** | `ROLE_OPEN_VERIFIED` / `ROLE_OPEN_NOT_VERIFIED` / `CONTACT TO VERIFY` / `ROLE_CLOSED` |

**Активность треда — не доказательство, что роль открыта.** `posts_count` и `last_posted_at`
двигаются потому, что **другие кандидаты** отвечают. Доказательство найма — свежий пост
**самого автора объявления**. Замер: у всех 14 тредов n8n в ранжировании
`last_poster_is_op = False`, а молчание автора — **от 23 до 570 дней**. Инструмент —
`tools/.t91/n8n_op_activity.py` (выход `n8n_op_activity.json`).

**Ловушка:** первая версия читала **хвост** `post_stream` — и вернула `op_age = None` для **всех
14** тредов. Причина: автор публикует объявление рано, дальше тред набивают кандидаты. Починено
адресным поиском `?q=@<op> topic:<id>`, который отдаёт **ровно посты этого автора в этой теме**.

Отсюда правило §6 брифа: живой тред без доказательства = `CONTACT TO VERIFY`, а не «открыто».
