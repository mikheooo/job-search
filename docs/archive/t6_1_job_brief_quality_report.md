## 3. Правка 1 — коммерческий и проектный опыт разведены

### Что было

`Assessment` держал один список `evidence`, и доказательства печатались в порядке
релевантности. Проектные факты (`project_stack`, `project_bullet`) называют больше технологий,
чем любая обязанность, поэтому в классе A они выигрывали сортировку и оказывались первыми —
под заголовком, который обещает оплачиваемую работу. На PHP/Bitrix24-вакансии там стоял
Reels Analyzer.

### Что сделано

```python
@property
def commercial_evidence(self) -> list[Evidence]:
    return [item for item in self.evidence if item.is_commercial]

@property
def project_evidence(self) -> list[Evidence]:
    return [item for item in self.evidence if item.origin == "project"]

@property
def resume_evidence(self) -> list[Evidence]:
    commercial = {id(item) for item in self.commercial_evidence}
    return [item for item in self.evidence
            if id(item) not in commercial and item.origin != "project"]
```

Печать в кратком виде (`_short_evidence_lines`):

* класс A — только `commercial_evidence` (до двух строк), затем, если тот же навык есть в
  собственном проекте, отдельная строка
  `— дополнительно, свой проект (не оплачиваемая работа): <имя>`;
* класс B — только `project_evidence`;
* остальные классы — `resume_evidence`.

Повышение до A по-прежнему невозможно по построению: `evidence_class = A` требует
`requirement.kind is COMMERCIAL_EXPERIENCE` **и** непустой `commercial` (то есть `duty` с
`role_id`) **и** `tenure.has_paid_work`. Проектный факт не несёт `role_id`, поэтому `is_commercial`
у него всегда `False`.

### Проверка на названных технологиях

Замер на реальной KB и реальных вакансиях (все требования класса A, где встречается
технология):

| Технология | Где проверено | Оплачиваемое доказательство | Свой проект |
| --- | --- | --- | --- |
| Bitrix24 | `habrcareer:1000168093` (`#Битрикс24`) | «Administered self-hosted Bitrix24…» (Bitrix24 Technical Support Specialist), «Developed n8n workflows connecting Bitrix24…» (AI Automation Engineer) | нет |
| Docker | `habrcareer:1000168093` (`#Docker`), `hh:136706048` | «Administered Linux and Docker infrastructure…» (AI Automation Engineer) | Reels Analyzer — отдельной строкой с пометкой |
| PostgreSQL | `hh:136706048` («SQL и PostgreSQL») | «Worked across Windows Server and Linux infrastructure, Active Directory, Exchange, SQL…» (Earlier IT Infrastructure & Support Experience) | Reels Analyzer — отдельной строкой с пометкой |
| Python | `himalayas:…senior-cyber-systems-administrator`, `weworkremotely:…uipath…`, `hh:136706048` | «Build asynchronous Python ETL pipelines with asyncio…» (AI Automation Engineer), «Automated routine administrative tasks with Bash and PowerShell.» (Earlier IT Infrastructure & Support Experience) | Reels Analyzer — отдельной строкой с пометкой |

Проверка «SQL и PostgreSQL» не выдумана: обязанность
`duty-39d5320cd4` = «Worked across Windows Server and Linux infrastructure, Active Directory,
Exchange, **SQL**, Hyper-V, networking, IP telephony, monitoring, API/web-service…» и она

Пин: `test_a_project_is_never_printed_as_paid_work_on_a_real_brief` проходит по всем пяти
вакансиям и требует, чтобы **любая** строка под заголовком подтверждённого опыта, называющая
проект, несла пометку «не оплачиваемая работа».

## 4. Правка 2 — нерелевантные предупреждения убраны из краткого вида

### Что было

`cannot_claim` собирался по всей KB и печатался целиком. В него входят `project_status`
внутренних экспериментов («TRACK B — PRONUNCIATION SCORER VALIDATION: `BLOCKED BY
STAGE_1_FINAL_NO_GO`»). На Bitrix24-вакансии эти две строки стояли в кратком отчёте и
вытесняли то, что действительно важно.

### Что сделано

Релевантность решается **связью, а не формулировкой** — предупреждение о проекте не называет
технологий, поэтому по словам его не отфильтровать:

* `project_status` несёт `parent_id` → проект. Предупреждение остаётся, только если этот проект
  используется требованием, у которого есть доказательства (класс не E);
* предупреждение без проекта остаётся, если называет технологию, которую вакансия просит.

Ничего не выброшено «потому что неприятно» — только потому что не относится к вакансии. Всё
отфильтрованное целиком печатается в `--details`.

### Замер

| Вакансия | Предупреждений в кратком | в `--details` |
| --- | --- | --- |
| IT Support | 0 | 2 |
| System Administrator | 0 | 2 |
| Bitrix24 Administrator | 0 | 2 |
| AI Automation Engineer | 0 | 2 |
| Python Developer | 0 | 2 |

`--details` по Bitrix24 заканчивается строкой:

```
## Что нельзя утверждать без подтверждения (весь KB)

- - **TRACK B — PRONUNCIATION SCORER VALIDATION**: `BLOCKED BY STAGE_1_FINAL_NO_GO` [project_status-608c03fb4e, project:39]
- Stage 1 остаётся **NO-GO**: текущая модель неустойчива между дикторами, а learner/error gold evidence отсутствует. [project_status-d67eb22b0d, project:11]

Для этой вакансии релевантны: 0 из 2.
```

Фильтрация не прячет настоящие ограничения: пин
`test_a_blocked_project_that_this_vacancy_uses_is_still_reported` строит KB, где проект с
пометкой `STAGE_1_FINAL_NO_GO` действительно используется ответом, и требует, чтобы
предупреждение осталось и в кратком виде.

## 5. Правка 3 — расчёт и трактовка стажа

Три отдельные ошибки, три отдельные правки.

### 5.1 Публикуется только утверждённая формулировка

```python
APPROVED_TOTAL_EXPERIENCE = "Общий опыт в IT: 15+ лет — подтверждено пользователем"
```

`Tenure.publishable()` возвращает ровно эту строку. Краткий вид печатает её и **ничего кроме**
неё. Проверено на всех пяти вакансиях:

```
tenure   : Общий опыт в IT: 15+ лет — подтверждено пользователем
```

`15.3` и `14.9` в кратком виде отсутствуют (пин по каждой из пяти вакансий).

### 5.2 `years_experience=3` больше не истолковывается

Раньше оговорка утверждала, что поле описывает специализацию, и ссылалась на 15.3. Это была
догадка, выданная за факт. Теперь:

> В профиле years_experience=3; что именно означает это поле, **не установлено**, поэтому оно
> не используется ни как общий стаж, ни как стаж в специализации.

Поле не подменяется на 15.3, не трактуется как стаж в AI/Python и не участвует в сравнении с
порогами вакансии.

### 5.3 Порог в годах не закрывается общим IT-стажем

`_technology_tenure_caveat()` добавляет к требованию:

> Вакансия называет срок N+ лет; стаж именно по этой технологии в KB не измеряется, и общий
> IT-стаж сюда не подставляется.

**Найденная дыра.** Оговорка висела только на ветке оплачиваемой работы и опиралась на
`matcher.extract_required_years`, который понимает цифровые формы («3+ years», «5+ лет») и
**не понимает** словесные. Замер по реальным требованиям:

| Требование (реальный текст) | `extract_required_years` | `_years_named` |
| --- | --- | --- |
| `At least five (5) years of Technical Lead experience…` | `None` | `5` |
| `Qualifications Education and Years of Experience: At least ten (10) years of hands-on experience in LAN/Network` | `None` | `10` |
| `At least five (5) years of progressive experience in enterprise and security architecture` | `None` | `5` |
| `Do you have two or more years of live technical support experience…` | `None` | `2` |
| `Required Experience UiPath Engineering Seniority: 3+ years…` | `3` | `3` |

То есть оговорка **не срабатывала ровно там, где она нужна**: на вакансии DMI требование
«At least five (5) years of Technical Lead experience» показывалось классом A без оговорки —
15 лет IT подставлялись вместо пяти лет руководства, то есть ровно то, что спека запрещает.

Добавлен `_years_named()`: сначала спрашивает матчер (цифровые формы сохраняют прежний смысл),
затем собственные шаблоны для словесных чисел. Оговорка теперь добавляется к объяснению
**любого** требования с порогом, независимо от класса, и дублируется одной строкой в кратком
виде под подтверждённым совпадением:

```
  • [пожелание] At least five (5) years of Technical Lead experience on system management /deployment projects with a focus on
      — Administered Linux and Docker infrastructure… (AI Automation Engineer)
      — Worked across Windows Server and Linux infrastructure, Active… (Earlier IT Infrastructure & Support Experience)
      — срок 5+ лет по этому требованию в KB не измеряется: общий IT-стаж сюда не подставляется
```

Замер: на пяти вакансиях оговорка добавляется к **5** требованиям — IT Support ×1,
System Administrator ×3, AI Automation Engineer ×1, Bitrix24 Administrator ×0,
Python Developer ×0. В кратком виде отдельной строкой она появляется **2** раза (IT Support,
System Administrator) — там, где требование с порогом стоит под подтверждённым совпадением
(класс A или B). На классах E и D оговорка остаётся в `--details`.

### 5.4 Оценка стажа осталась, но под запретом публикации

`--details` по-прежнему показывает хронологию и оценку — она нужна как ворота, — но под
заголовком «Ниже — внутренняя оценка по хронологии KB. Она НЕ утверждена и не публикуется»:

```
Оценка (не утверждена): IT ≈ 15.3 г.; оплачиваемая работа ≈ 14.9 г.; неоплачиваемые свои проекты ≈ 0.4 г.
Почему не публикуется: это арифметика по датам ролей, где часть дат указана только годом
(год без месяца читается как январь/декабрь), поэтому оценка сдвигается на срок до года.
Утверждённая формулировка общего опыта — «Общий опыт в IT: 15+ лет — подтверждено пользователем».
```

Пин `test_the_estimate_is_shown_only_under_an_unapproved_label` требует, чтобы пометка
«НЕ утверждена» шла **раньше** числа, а не после.

## 6. Правка 4 — качество краткого отчёта

Порядок ровно по спеке: вакансия и условия → подтверждённые совпадения → частичные →
обязательные требования без подтверждения → несколько уточнений, влияющих на отклик.

Что изменилось:

* класс E больше не попадает в цикл подтверждённых совпадений — у него свой раздел
  «ОБЯЗАТЕЛЬНЫЕ ТРЕБОВАНИЯ БЕЗ ПОДТВЕРЖДЕНИЯ»; пожелания без подтверждения свёрнуты в одну
  строку «Пожелания без подтверждения: …»;
* уточнений не больше трёх (было шесть);
* длинные цитаты обрезаются по границе слова, а обрывок с незакрытой скобкой отбрасывается
  целиком («…(systemd services» больше не появляется);
* идентификаторы сервисов (`claim_id`, `DERIVED_FROM_SOURCE`, `source_file`, `project-…`) в
  кратком виде отсутствуют — пин на всех пяти вакансиях;
* зарплата без валюты не сравнивается с минимумом кандидата: «24 (валюта в источнике не
  указана) — сравнить нельзя, минимум кандидата $1000»;
* «Отсутствие подтверждения в доступных источниках — не доказательство отсутствия навыка»
  печатается всегда, когда класс E непуст.

* **IT-стаж не превращается в стаж по Python** — требования с порогом в годах несут оговорку;
* **неподтверждённые требования не объявляются отсутствующими навыками** — раздел называется
  «БЕЗ ПОДТВЕРЖДЕНИЯ», рядом стоит оговорка; текста вида «не хватает опыта» нет;
* **неизвестная валюта не сравнивается с USD** — `salary_meets_minimum is None`, строка
  «сравнить нельзя», слов «НИЖЕ минимума» и «выше минимума» нет.

Замечание, вынесенное наружу без правки: на вакансии DMI в списке обязательных требований без
подтверждения стоит строка `Requirements: None required for this position` — это дословная
строка вакансии, а не выдумка экстрактора, но на телефоне она читается как требование. Правка
потребовала бы менять извлечение требований, то есть перестраивать матчер, чего T6.1 не делает.
