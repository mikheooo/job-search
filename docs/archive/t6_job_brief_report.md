## 1. Что реализовано

Модуль `ai_assistant/candidate/job_brief.py` — «Job-to-Candidate Brief»: читает конкретную вакансию,
сопоставляет её требования с фактами KB и раскладывает результат по классам A–E.

Что он делает по шагам:

1. **Сегментация описания.** Реальные описания в `state.db` хранятся **одной строкой без переводов
   строк** (замер: 272 символа, 0 `\n` у habr-вакансии; 5293 символа, 0 `\n` у We Work Remotely).
   `segment()` режет их по маркерам списков, эмодзи, границам предложений и стандартным заголовкам
   секций. Именно из-за этого дефекта старый `job_analyzer._fallback_analysis` («первые три
   предложения») выдумывал требования — T6 его не использует.
2. **Извлечение фактов.** Название, работодатель, обязанности, обязательные требования, пожелания,
   технологии, требуемый коммерческий стаж, язык работы, формат/география, зарплата. Отсутствующее
   помечается как «не указано» и попадает в список `unstated` — не выдумывается.
3. **Классификация требований** A–E (см. §3).
4. **Подтверждённые предпочтения** из пяти интервью-фактов KB: приоритет, минимальный доход,
   Bitrix24 наравне, хронология, свои проекты без оплаты.
5. **Конфликты с активными фильтрами** — отдельным списком, без изменения самих фильтров.
6. **Три вида вывода:** короткий (телефон), подробный (`--details`), JSON (`--json`).

### Что переиспользовано (второй матчер и вторая база кандидата НЕ создавались)

| Компонент | Откуда | Как используется |
| --- | --- | --- |
| `CandidateKnowledgeBase` | `ai_assistant/candidate/kb.py` | единственный источник фактов |
| `load_kb()` | `candidate/master_resume.py` | загрузка KB из `candidate_kb.json` |
| `ClaimStatus`, `is_project_sourced` | `candidate/kb.py` | статусы и происхождение фактов |
| `extract_required_years`, `extract_seniority` | `ai_assistant/matcher.py` | стаж и уровень — тестируемыми хелперами, а не новыми регексами |
| `classify_work_format` | `ai_assistant/remote_filter.py` | формат работы |
| `get_vacancy_by_id`, `_row_to_vacancy` | `ai_assistant/db.py` | чтение вакансии из `state.db` |
| `DEFAULT_SEARCH_QUERIES` | `ai_assistant/hh_autonomous_agent.py` | для сверки фильтров с предпочтениями |
| `MUST_HAVE_MARKERS`, `NICE_TO_HAVE_MARKERS` | `ai_assistant/job_analyzer.py` | **общий словарь** must/nice |

Словарь `MUST_HAVE_MARKERS` / `NICE_TO_HAVE_MARKERS` вынесен в `job_analyzer.py` (16 вставок,
2 удаления, поведение не изменилось) именно для того, чтобы T6 и существующий анализатор не
разошлись в понимании того, что считать требованием. Проверено: `ruff` по `job_analyzer.py` даёт
те же 6 находок, что и `HEAD`, сдвинуты только номера строк.

### Ключевое ограничение честности, заложенное в модель

В KB **только `duty`-факты несут `role_id`** — то есть только они привязаны к работодателю.
Факты о навыках (`skill`) несут `parent_id` → группу навыков, но не роль. Поэтому:

* **класс A** (коммерческий опыт) достижим только через `duty` с `role_id`;
* **класс B** — через проектные факты (`project*`), и он **структурно не может** стать A;
* голый `skill` без роли — это **класс D**, а не A.

Это не эвристика поверх данных, а свойство самой KB: выдать свой проект за оплачиваемую работу
модуль не может по построению.

## 3. Как читается классификация A–E

| Класс | Значение | Чем подтверждается |
| --- | --- | --- |
| **A** | подтверждено опытом работы | `duty` с `role_id` (оплачиваемая роль) |
| **B** | закрывается своим проектом (не оплачиваемая работа) | проектный факт |
| **C** | частично | своя разработка при требовании коммерческого опыта, или близкая технология |
| **D** | есть в резюме, нужно уточнение | `skill`/`summary` без привязки к роли |
| **E** | нет подтверждения в источниках | ничего не нашлось |

Класс E **всегда** сопровождается оговоркой: «Отсутствие подтверждения в доступных источниках —
не доказательство отсутствия навыка». Отсутствие подтверждения не печатается как отсутствие навыка.

## 4. Команда запуска

```
python -m ai_assistant.cli candidate-job-brief --vacancy "<stable_id>" [--details] [--json] [--out PATH]
```

Три взаимоисключающих источника вакансии: `--vacancy` (уже есть в `state.db`, читается только на
чтение), `--text` (строка), `--file` (файл). Плюс `--kb`, `--profile`, `--details`, `--json`, `--out`.

Полная справка:

```
usage: cli.py candidate-job-brief [-h] [--vacancy VACANCY] [--text TEXT]
                                  [--file TEXT_FILE] [--kb KB]
                                  [--profile PROFILE] [--details] [--out OUT]
                                  [--json]

  --vacancy VACANCY  stable_id of a vacancy already in state.db (read-only)
  --text TEXT        Vacancy description as an inline string
  --file TEXT_FILE   File holding the vacancy description
  --kb KB            Path to candidate_kb.json (default: repo root)
  --profile PROFILE  Path to candidate_profile.json (default: auto-discover)
  --details          Full version with claim ids, statuses and sources
  --out OUT          Write the brief to this path instead of stdout
  --json             Output as JSON
```

## 6. Проверка источников и статусов

Подробный вывод (`--details`) печатает по каждому требованию `claim_id`, вид факта, статус, роль или
проект и ссылку `файл:строка`. Пример (та же Bitrix24-вакансия):

```
| № | Класс | Обязательно | Требование | Доказательство |

| 2 | E | да | #JavaScript | — |
| 6 | C | да | #GitLab | — |
| 9 | A | да | #Docker | duty-464bce9700 (resume, DERIVED_FROM_SOURCE, resume.md:31); project_stack-a4e7dce20e (project, ..., README.md:38); skill-68a2a982ea (resume, ..., resume.md:12); summary-865c184449 (resume, ..., resume.md:7) |
```

Источники и статусы не теряются: у каждого доказательства есть `claim_id`, `ref` и `status`.
Порядок доказательств внутри класса A — сначала оплачиваемая работа (`duty-464bce9700`,
`resume.md:31`), потом проектные факты: строка «ПОДТВЕРЖДЕНО ОПЫТОМ РАБОТЫ» не может открываться
своим проектом.

## 8. Что нашлось и было исправлено по ходу проверки

Пять дефектов, найденных при прогоне T6 по реальным вакансиям, — все с тестом-пином:

1. **Строка тегов считалась одним требованием.** `Требуемые навыки: #middle, #Битрикс24,
   #JavaScript, #PHP, #MySQL, #CI/CD, #GitLab, #RabbitMQ, #Jira, #Docker` — одно требование.
   Одно совпадение (Docker) помечало весь блоб как «ПОДТВЕРЖДЕНО ОПЫТОМ РАБОТЫ», и бриф молча
   приписывал PHP, JavaScript, MySQL и RabbitMQ. Теперь каждый тег отвечает сам за себя:
   `must=9, A=2, C=1, E=6` вместо `must=1, A=1`.
2. **Точка в конце тега попадала внутрь тега.** `#Docker.` → `docker.`, что не совпадает ни с
   одной технологией KB и дало бы ложный класс E для подтверждённого навыка. Точка срезается
   только концевая, поэтому `#asp.net` и `#node.js` сохраняют свои.
3. **В классе A первым печаталось доказательство из своего проекта.** `project_stack` называет
   больше технологий, чем любая обязанность, и выигрывал сортировку по релевантности: на
   `hh:136706048` требование PostgreSQL открывалось двумя буллетами Reels Analyzer под заголовком
   «ПОДТВЕРЖДЕНО ОПЫТОМ РАБОТЫ». Теперь порядок зависит от класса: A ведёт оплачиваемым, B — проектом.
4. **Метка списка вклеивалась в текст требования.** Вопрос читался «Есть ли опыт с «Требуемые
   навыки: #JavaScript»?», а хайлайт — «Опыт работы — Требуемые навыки: #Битрикс24». Теги
   печатаются голыми (`#JavaScript`), а обязательность наследуется от метки — иначе список
   «Требуемые навыки:» молча стал бы списком пожеланий.
5. **Зарплата без валюты приглашала к сравнению.** Было «24 (валюта в источнике не указана) —
   минимум кандидата $1000», читается как «24 против 1000». Стало «— сравнить нельзя, минимум
   кандидата $1000»: сравнение действительно не делалось.

## 9. Ограничения и нужные уточнения

### Ограничения T6

* **Не меняет ничего за пределами вывода.** Резюме, профиль, KB, статусы фактов, `state.db`,
  активные фильтры и правила отправки откликов не тронуты. Реальных откликов не было.
* **Не подключён к автоотправке.** T6 — только чтение и отчёт.
* **Не выдумывает достижения.** Все утверждения берутся из фактов KB со ссылкой; LLM не
  используется вовсе.
* **Класс E — это «не нашёл», а не «нет».** Формулировка напечатана рядом с классом.
* **«НЕЛЬЗЯ ПИСАТЬ В ОТКЛИК БЕЗ ПОДТВЕРЖДЕНИЯ» — список глобальный.** Он показывает факты
  `project_status`/`conflict_notes` (например, NO-GO по pronunciation scorer), не связанные с
  конкретной вакансией. Это защитная сетка «это нельзя утверждать нигде», но на телефоне она
  выглядит шумом рядом с Bitrix24-вакансией. Если мешает — стоит ограничить список теми фактами,
  что пересекаются с требованиями вакансии.
* **Обязательность для строки тегов берётся из метки.** Список без метки («Стек: #PHP, #MySQL,
  #Docker») считается пожеланием — как и раньше, до правки.
* **`Формат: не удалённо` при тексте «Можно удалённо»** — это существующее намеренное правило
  `remote_filter.py` (условная удалёнка отвергается, см. докстринг модуля), а не дефект T6.
  Для вакансии из Москвы это верно, но если правило мешает по кандидатам, готовым к гибриду,
  менять его надо в `remote_filter`, а не в T6.

### Нужны решения Миши

1. **Фильтры противоречат подтверждённым предпочтениям** — T6 их не меняет и печатает списком:
   * `minimum_salary`: 1500 → 1000 USD (подтверждено на интервью);
   * `excluded_roles` / `must_avoid_conditions`: Bitrix24 в исключениях → рассматривать наравне;
   * `years_experience`: 3 → 15.3 по хронологии KB;
   * `DEFAULT_SEARCH_QUERIES`: нет запросов по IT Support, System Administration, Bitrix24/CRM.
2. **T5.2 не применён.** Четыре утверждённые правки мастер-резюме отсутствуют — этап числится
   незавершённым, и текст мастер-резюме не считается утверждённой публичной версией.
3. **Ратчет `docs/ble001_triage.md` красный** (24 при пороге 18) — отдельно от T6.
