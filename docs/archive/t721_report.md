## B. NEW BROWSER PROVIDER / MODE

Новый модуль: **`ai_assistant/hh_browser_provider.py`** (1076 строк). Приём тот же, что у
`autonomous_mode.py`: старая точка входа остаётся, решение о браузере уезжает в отдельный модуль.

### B.1. Режимы

```
MODE_ENV      = "HH_BROWSER_MODE"
MODE_HEADLESS = "headless"      ← продакшн и умолчание
MODE_BROWSEROS= "browseros"     ← откат/отладка
DEFAULT_MODE  = MODE_HEADLESS
```

`browser_mode()` читает env и **падает** `UnknownBrowserMode` на опечатку. Никакой магии
«а вдруг 9110 свободен»: режим задаётся явно, `.env` содержит `HH_BROWSER_MODE=headless`.

### B.2. Приоритет адреса

```
resolve_browser_endpoint(preferred=None)
  1. mode == browseros            → исторический resolve_cdp_url(...)   (9110 / 9222 / пин)
  2. явный preferred ≠ умолчание  → он (явный адрес = решение)
  3. пин CDP_URL                  → он
  4. иначе                        → http://127.0.0.1:9111
```

**`HH_CDP_URL` в headless-режиме не читается вообще.** Иначе адрес 9110 утаскивал бы каждый
headless-прогон обратно на BrowserOS. `HH_CDP_URL` остался в `.env` — он снова оживает только
при `HH_BROWSER_MODE=browseros`.

### B.3. Куда переехали вызовы

| файл | было | стало |
|---|---|---|
| `hh_browser_launcher.py` | — | `+ cdp_url_pin()`, `+ resolve_browser_endpoint()` (ре-экспорт); `ensure_hh_browser` умеет headless-ветку |

## C. HEADLESS LAUNCHER

### C.1. argv

```python
headless_argv(chrome_exe) →
  ["C:\Program Files\Google\Chrome\Application\chrome.exe",
   "--headless=new",
   "--remote-debugging-address=127.0.0.1",
   "--remote-debugging-port=9111",
   "--user-data-dir=C:\Users\Misha\AppData\Local\JobSearchHeadless\User Data",
   "--no-first-run", "--no-default-browser-check",
   "--window-size=1440,900", "about:blank"]
```

**Это список, а не строка.** `subprocess.Popen(argv)` без шелла — ровно потому, что в пути
есть пробел: `--user-data-dir=...\User Data` обязан быть **одним** аргументом. T7.20 сломался
именно на этом (через `Start-Process` путь распался, и на диске появился мусорный каталог
`...\JobSearchHeadless\User`). Живая проверка подтвердила: в командной строке процесса аргумент
приходит целиком, в кавычках:

```
CMDLINE "...\chrome.exe" --headless=new --remote-debugging-address=127.0.0.1
        --remote-debugging-port=9111 "--user-data-dir=C:\Users\Misha\AppData\Local\JobSearchHeadless\User Data"
        --no-first-run --no-default-browser-check --window-size=1440,900 about:blank
```

### C.2. Три отказа «громко и ничего не трогая»

`launch_headless()` проверяет **до** запуска:

| проверка | поведение |
|---|---|
| порт отвечает, но это **не наш** headless | `error: "... is not a headless Chrome (Chrome/151...); refusing to drive or replace it"` |
| профиль занят живым нашим инстансом | `error: "the dedicated profile ... is already held by a live instance (pid N)"` |
| `chrome.exe` не найден | `error: "Google Chrome was not found ... set CHROME_PATH"` |

Порт проверяется **сокетом** (`port_is_listening`), а не `curl`: curl на localhost идёт через
прокси, и мёртвый upstream отдаёт `502` с кодом возврата `0` — ложный «порт занят» (грабля T7.20).

«Наш ли это инстанс» решается по UA-маркеру `HeadlessChrome` в ответе `/json/version`.

### C.3. Ожидание готовности

После `Popen` — цикл до `CDP_STARTUP_TIMEOUT = 30 s`: если процесс уже умер, отдаём
`"Chrome exited with code N before CDP answered"`; иначе опрашиваем `/json/version` каждые 0.4 s.
Запуск идёт с `DETACHED_PROCESS | NEW_PROCESS_GROUP` — дочерний процесс не привязан к нашей консоли.
Лог — `artifacts/headless-poc/chrome-headless.log`.

### C.4. Сессия и уборка

`HeadlessBrowserSession` держит **одну рабочую вкладку** (создаётся один раз, дальше
переиспользуется) и помнит **все** открытые ею вкладки. `tab()` закрывает свою вкладку сам,
`stop()` — остальные, затем браузер.

```
stop() → close_all_tabs() → Browser.close → wait_port_free(20 s)
       → запись {"pid": null, "stopped_at": ...} в runner-state.json
```

Состояние **записывается, а не удаляется**: удаление файла — это бухгалтерия, и она не имеет
права быть тем, что ломает выключение (замерено: песочница заблокировала `unlink`, и чистый
стоп превратился в код возврата 1 без отчёта). `profile_in_use()` и так считает мёртвый PID
свободным.

**`Browser.close` отправляется без ожидания ответа** — соединение рвётся вместе с процессом.

## D. AUTH GATE

Перед любой приватной работой — проверка входа. Никакого авто-логина, никакого копирования
cookie, никакого обхода.

`decide_authentication(evidence)` — **чистая функция**, тестируется таблицей:

| признак в DOM | вердикт |
|---|---|
| `login_card_visible` или `login_input_present` | `authenticated=False, verified=True` |
| `profile_link_href` содержит `account/login` | `authenticated=False, verified=True` |
| `hhrole == "anonymous"` | `authenticated=False, verified=True` |
| `applicant_ui_present` и карточки входа нет | `authenticated=True, verified=True` |
| ни то, ни другое | `authenticated=False, verified=False` — «страница не доказывает ничего» |

При `HH_AUTH_REQUIRED` возвращается сообщение **«Нужен ручной вход в профиль JobSearchHeadless.»**,
а сессия **гасит себя сама** (`start()` вызывает `stop()` перед возвратом) — раннер не остаётся
висеть с чужим неавторизованным Chrome.

**Ловушка, поймана живьём.** Первый живой прогон гейта ответил `HH_AUTH_REQUIRED` на **валидной**
сессии. Причина: страница читалась сразу после `/json/new` — пустой документ выглядит ровно как
разлогиненный профиль. Лечение: `check_auth()` сначала **навигирует**, затем опрашивает до
`auth_attempts = 10` раз, ожидая реальных признаков отрисовки. Живой ответ после правки:

```
authenticated: true, verified: true
reason: "applicant UI is rendered and no login card is present"
h1: "Михаил Колесников" · path: /applicant/profile/me · hhrole: "applicant"
```

### E.4. Ловушка навигации (иначе весь прогон — ложь)

`navigate()` ждёт **двух** условий, оба обязательны:

1. `readyState == "complete"`, **и**
2. URL **изменился** — не «равен запрошенному», а именно изменился.

`readyState` в одиночку недостаточно: свежая вкладка уже `complete` на `about:blank`, ожидание
возвращается мгновенно со **старым** документом, и следующее чтение отвечает про пустую страницу.
Замерено: на первом живом прогоне вакансия отрисовывалась идеально (скриншот это подтверждал),
а чтение возвращало **все поля `null`**. Второе условие — «изменился», а не «равен», потому что
HH **редиректит**: `/applicant/resumes` уезжает на `/applicant/profile/me`.

  2637.8 MB / 20), а не ниже. Причина — **не забытые вкладки**, а стоимость renderer'а на вкладку:
  19 renderer'ов на 5 вкладок (по одному на фрейм/сайт-процесс), крупнейшие — по 240–350 MB.
  Это свойство Chrome на тяжёлых страницах HH, а не утечка в коде. Лечится не «уборкой вкладок»,
  а ограничением их числа и повторным использованием одной рабочей вкладки — что уже сделано
  (`ensure_work_tab` создаёт вкладку один раз).
- **Чего делать не стали.** Искусственных трюков с памятью (`--single-process`,
  `--js-flags="--max-old-space-size"`, `--disable-dev-shm-usage`) нет: причина названа, и она
  не в них. Если на VM 964 МБ это станет проблемой — решение отдельное (лимит вкладок / вынос
  на отдельную машину), и его нужно принимать явно, а не прятать флагом.

## J. REMAINING RISKS

1. **Пик памяти выше T7.20, а не ниже** (26 проц. / 3144.9 MB на 5 вкладках против 20 / 2637.8).
   Утечки нет — после выключения 0 процессов и 0 MB, — но цена renderer'а на вкладку реальна.
   На VM 964 МБ это надо решать отдельно (лимит вкладок либо вынос на другую машину).
2. **Путь записи через headless не проверялся и остаётся закрытым.** Отправка отклика идёт через
   прежние боевые ворота (`SUBMIT_ALLOWED`), семантика не менялась. Это **осознанное ограничение**:
   T7.21 проверял чтение, и первым, что откроется на новом пути, отклик быть не должен.
3. **Ратчет `test_report_line_refs` = 24 при пороге 18** — пре-существующий долг, оставлен как есть.
   Порог не поднимался.
4. **`select_best_hh_target` по-прежнему адресует вкладку подстрокой URL.** В новом провайдере
   `Runtime.evaluate` идёт **по `targetId`**, так что сам раннер этой ловушке не подвержен, —
   но старый хелпер жив и продолжает использоваться в легаси-путях.
5. **Профиль `JobSearchHeadless` живёт на `C:` и хранит сессию HH в открытом виде** — как и
   любой Chrome-профиль. Права наследуются от пользователя; отдельного шифрования нет и не
   предполагалось.
6. **`browseros`-ветка не покрыта живьём дальше резолва адреса и версии.** Проверено, что
   адрес резолвится и порт отвечает; полноценный приватный прогон через 9110 в этой задаче
   не гонялся (и не требовался — он был бы шагом назад).
7. **Режим читается из env один раз на процесс.** Смена `HH_BROWSER_MODE` внутри долгоживущего
   процесса (UI, демон) не подхватится без перезапуска. Для CLI это не проблема.
8. **«Прогон при выключенном BrowserOS» буквально не выполнялся** — BrowserOS был запущен
   (pid 7608, старт 13:26:27), а останавливать его §5 запрещает. Независимость доказана строже,
   прогоном §E.3 с мёртвым пином 9199, но это **не** то же самое, что буквальный сценарий
   «BrowserOS отсутствует». Если нужен именно он — его надо проверять в момент, когда BrowserOS
   действительно выключен, и это отдельное решение Миши, а не моё.
